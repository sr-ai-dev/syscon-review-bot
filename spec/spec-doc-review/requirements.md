# Spec Document Review 요구사항

## 배경

리뷰 봇은 현재 PR의 스펙·요구사항과 코드 변경의 정합성, 아키텍처, 코드 품질을 검토한다. 하지만 스펙 문서 자체가 모호하거나 `requirements.md`, `design.md`, `tasks.md` 사이에 불일치가 있어도 이를 별도 finding으로 노출하지 않는다.

스펙 문서 품질 문제가 있으면 구현자가 요구사항을 잘못 해석할 수 있고, 코드 정합성 리뷰도 신뢰하기 어렵다. 따라서 코드 정합성보다 먼저 스펙 문서 자체를 검토해야 한다.

## 요구사항

- 리뷰 결과 모델은 스펙 문서 결함을 코드 정합성 불일치와 별도로 표현해야 한다.
- 스펙 문서 결함은 리뷰 본문에서 가장 먼저 표시되어야 한다.
- 스펙 문서 결함이 1건 이상 있으면 최종 판정은 `수정 필요`여야 한다.
- 스펙 문서 finding은 다음 정보를 포함해야 한다.
  - 파일 경로
  - 라인 번호
  - 설명
  - 제안
  - 신뢰도
- 리뷰 본문에서 신뢰도는 별도 컬럼이 아니라 각 항목 마지막 줄에 간략히 표시해야 한다.
- 스펙 문서 검토 기준은 다음 항목을 포함해야 한다.
  - 완결성
  - 일관성
  - 검증 가능성
  - 범위 명확성
  - 추적성
  - 리스크 명시
- 단순 취향, 문서 스타일 선호, "더 자세하면 좋음" 수준의 지적은 스펙 문서 finding으로 등록하지 않아야 한다.
- 기존 mismatch, architecture finding, quality finding 동작은 유지해야 한다.
- 이전 리뷰 상태 판정과 judge/postprocess 단계는 스펙 문서 finding을 다른 finding과 동일하게 처리해야 한다.
- 사용자 문서는 스펙 문서 검토 기준과 리뷰 본문 표시 순서를 설명해야 한다.

## 수용 기준

- 스펙 문서 finding이 있는 리뷰 결과는 `Decision.REQUEST_CHANGES`로 계산된다.
- 리뷰 본문은 `스펙 문서 검토` 섹션을 `스펙과 불일치`, `아키텍처 검토`, `코드 품질 검사`보다 앞에 표시한다.
- finding 표에는 `conf` 컬럼이 없고, 각 항목 본문 마지막 줄에 `신뢰도: <값>`이 표시된다.
- LLM 출력 JSON 스키마에는 `spec_doc_findings`가 포함된다.
- `spec_doc_findings`가 없는 기존 JSON 응답은 기본 빈 배열로 처리된다.
- README에는 스펙 문서 검토 기준과 표시 방식이 문서화된다.
